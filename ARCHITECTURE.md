# Архитектура

## Сервисы

```
 браузер ──► caddy :3000 ──► web × N (Next.js 16, standalone) ──► postgres
    │                          │  ▲                            ──► redis (BullMQ, pub/sub, лимиты)
    │                          │  └── SSE /api/events ◄── redis pub/sub
    │                          ▼ presigned URL / 302 на сегменты
    └── PUT частей, GET медиа ──► minio (S3) ◄── worker × N (ffmpeg) ──► mailpit
                                                    │ очереди: media, transcribe, email, maintenance
               migrate (одноразовый)                ├──► whisper (профиль transcription)
                                                    └──► jaeger ◄── web (профиль observability)
```

- **Файлы не проходят через Next.js.** Части загружаются в MinIO напрямую, видео отдаётся оттуда же. Web только проверяет права и подписывает URL.
- **Caddy** — единственная точка входа. Список экземпляров web он берёт из DNS Docker (`dynamic a`), поэтому `--scale web=N` работает без настройки. В web нет состояния: сессии в Postgres, события в Redis.
- **Worker** — отдельный процесс и контейнер. Код схемы БД, очередей и писем у него общий с web, а React — нет.

## Путь файла: от браузера до HLS

1. **Браузер.** `FileUpload` ([upload-file.ts](src/features/uploads/upload-file.ts)) — TS-класс без React: 4 части параллельно, повторы с backoff, пауза, отмена. SHA-256 считается потоково в Web Worker.
2. **Возобновление.** Каждая готовая часть (номер + ETag) записывается в IndexedDB под ключом «проект + ассет + имя + размер + SHA-256 первых 4 МБ». Когда файл выбирают снова, `GET /api/uploads/:id` возвращает `ListParts` из S3, и докачиваются только части, у которых ETag совпадает и в записи браузера, и в S3.
3. **`POST /api/uploads`.** Проверка роли, MIME и размера, `CreateMultipartUpload`. Папки перетащенного каталога создаются на сервере (insert-or-select по уникальному «родитель + имя»).
4. **`/parts`.** Presigned URL выдаются пачкой, права проверяются на каждом вызове.
5. **`/complete`.** `CompleteMultipartUpload`, `HeadObject`, затем транзакция под `FOR UPDATE`: версия (номер считается под блокировкой ассета), устаревание активного ревью. После коммита задача уходит в очередь с `jobId = versionId`.
6. **Worker.** Скачивает оригинал и в том же проходе сверяет SHA-256, ffprobe определяет, что это на самом деле. Затем одно кодирование в **HLS 720p + 360p** (fMP4-сегменты по 4 с, ключевой кадр каждые 2 с в обоих качествах), 720p MP4 копированием из HLS (без второго кодирования), спрайт до 100 миниатюр, постер. Всё кладётся по фиксированным ключам `versions/<id>/…`, поэтому повтор задачи идемпотентен.
   - **Точность кадра.** В fMP4 нет edit list, поэтому задержка B-кадров и AAC сдвигала бы видео на 23–66 мс, а на 29.97 fps это почти кадр. Поэтому кодирование идёт с `-bf 0`, аудио — отдельной HLS-группой, с `-avoid_negative_ts disabled`. В Chromium проверено через `requestVideoFrameCallback`: кадры 0, 1799, 1800 показываются ровно те, что запрошены.
7. **Отдача HLS.** Плейлисты (несколько КБ) отдаёт наш route как есть, на каждый сегмент он отвечает 302 на presigned URL с TTL 60 с ([hls.ts](src/features/player/hls.ts)). Подписанные URL не протухают посреди просмотра, а права (и отзыв публичной ссылки) проверяются на каждом сегменте. Буфер hls.js ограничен 30 секундами, чтобы эти проверки имели силу.
8. **Прогресс и надёжность.** Прогресс публикуется в Redis, в Postgres пишется каждые 5%, в браузер приходит по SSE. Sweeper переотправляет `pending`-версии без задачи, брошенные multipart-загрузки старше суток прерываются. `x-request-id` и трейс OpenTelemetry идут от `complete` до worker.

## Модель прав

- Роли упорядочены: `owner > editor > reviewer > viewer`. Таблица «действие → минимальная роль» лежит в [roles.ts](src/features/workspaces/roles.ts) и общая для сервера и UI.
- Сервер проверяет членство JOIN-ом на каждом запросе, без кеша в сессии. Нет доступа — **404**, а не 403.
- **Публичные ссылки.** В БД хранится только SHA-256 токена, URL показывается создателю один раз. Каждый гостевой запрос (страница, плейлист, сегмент, комментарий) заново читает ссылку, поэтому отзыв действует сразу. Гость, введший пароль, получает свою сессию (случайный токен, в БД хеш) в cookie с `Path=/s/<token>`. Пароль проверяется с лимитом в Redis: 10 ошибок с IP и 50 на ссылку за 15 минут. Медиа-URL гостей живут не дольше 5 минут, страница гостя раз в 10 секунд проверяет `/status`.
- **CSRF.** `proxy.ts` сравнивает `Origin` с `APP_URL` для изменяющих запросов к `/api/*` и `/s/*`. Server Actions защищает сам Next.
- **CSP.** Nonce на каждый запрос, `script-src 'self' 'nonce-…' 'strict-dynamic' 'wasm-unsafe-eval'`, без `unsafe-inline` ([csp.ts](src/lib/csp.ts)). Все страницы рендерятся динамически, чтобы на каждой был nonce. `'wasm-unsafe-eval'` разрешает только компиляцию WebAssembly (хеширование), но не `eval`. `style-src` оставлен с `'unsafe-inline'` из-за style-атрибутов плеера: стили не исполняют код.

## Realtime

- Изменения публикуются в Redis-канал `events:project:<id>`. Каждый экземпляр web держит **одно** подписочное соединение и раздаёт сообщения своим SSE-потокам, поэтому несколько экземпляров видят все события.
- В браузере один `EventSource` на страницу. Комментарии применяются чистым reducer'ом с дедупликацией по id: id генерирует клиент, поэтому оптимистичная копия, ответ API и эхо по SSE дают одну запись.
- Если Redis недоступен, поток не рвётся, а UI показывает «Live updates are paused». При SIGTERM потоки закрываются, и браузер переподключается к живому экземпляру.

## Согласование

- Правила — чистые функции [rules.ts](src/features/reviews/rules.ts). `any`: первое решение закрывает шаг. `all`: все approve или первый request changes. `atLeast N`: N одобрений или changes requested, как только N уже не набрать. Шаги последовательные, до 5.
- Решение принимается в транзакции: `SELECT … FOR UPDATE` строки запроса выстраивает одновременные клики в очередь, затем `applyDecision`, и решение, новый шаг и итоговый статус ассета пишутся в той же транзакции. Повтор с тем же `Idempotency-Key` возвращает тот же результат. Одно активное ревью на ассет гарантирует частичный уникальный индекс.
- Письма и события уходят после коммита. Напоминание за сутки — отложенная задача BullMQ.

## Server и Client Components

| Часть | Тип | Почему |
|---|---|---|
| Layout, inbox, workspaces, список ассетов, папки, тулбар | Server | Данные; состояние списка в URL, переключатели — обычные `<Link>` |
| Бейджи обработки, `ProjectEvents` (SSE) | Client | `EventSource` |
| Загрузчик, «New version» | Client | File API, XHR, IndexedDB, Web Worker |
| Формы (auth, workspaces, папки, ссылки, мастер ревью) | Client (только форма) | React Hook Form + общие zod-схемы |
| Страница ассета: метаданные, версии, панель ревью, ссылки | Server | Данные; кнопки — клиентские островки |
| `ReviewWorkspace`: плеер, таймлайн, комментарии, аннотации, транскрипт; сравнение версий; страница гостя | Client | Общий `<video>`; время плеера не в state |

**Мутации.** Где в разделе 4 ТЗ есть эндпоинт (загрузки, комментарии, ревью, ссылки), UI ходит в него `fetch` (нужны `If-Match`, `Idempotency-Key`, коды 409/412). Остальное делается Server Actions.

**i18n.** Словари `en`/`ru` — обычные TS-объекты. Тип `ru` выводится из `en`, поэтому пропущенный перевод — ошибка компиляции. Клиенту передаётся только код локали. Сообщения общего кода (zod, ошибки API, worker) написаны по-английски и переводятся при показе по английскому тексту как по ключу ([translate.ts](src/i18n/translate.ts)). Серверную логику ради перевода не пришлось трогать.

## Производительность

Главное решение: **время видео не хранится в React state.** Таймкод, бегунок и превью из спрайта обновляются через `requestAnimationFrame` и ref прямо в DOM ([use-video-time.ts](src/features/player/use-video-time.ts)). Незаконченная фигура — локальный state слоя рисования (portal поверх видео).

**Замер (Chromium, M-серия, видео 1080p).** 500 маркеров и 300 тредов, 3 секунды воспроизведения: кадры p95 **16.7 мс**, ни одного дольше 50 мс; **0** изменений DOM вне таймкода и бегунка; во время рисования **0** изменений в списке комментариев.

**Как воспроизвести:**
1. Создать 500 комментариев:
   ```sql
   insert into comments (id, version_id, author_id, body, timecode_ms, created_at)
   select gen_random_uuid(), '<version_id>', (select id from users where email='editor@example.com'),
          'Note #' || g, g * 299, now() - (500 - g) * interval '1 second'
   from generate_series(1, 500) g;
   ```
2. Открыть ассет, 14 раз нажать «Load more comments», запустить воспроизведение и выполнить в консоли:
   ```js
   const ok = [document.querySelector("span.font-mono"), document.querySelector('[role="slider"]')];
   let outside = 0; const deltas = []; let last = performance.now();
   const mo = new MutationObserver((rs) => rs.forEach((r) => { if (!ok.some((e) => e.contains(r.target))) outside++; }));
   mo.observe(document.body, { subtree: true, childList: true, characterData: true, attributes: true });
   const tick = (t) => { deltas.push(t - last); last = t; if (deltas.length < 180) requestAnimationFrame(tick);
     else { mo.disconnect(); deltas.sort((a, b) => a - b); console.log({ outside, p95: deltas[171], max: deltas.at(-1) }); } };
   requestAnimationFrame(tick);
   ```

## От чего отказались

- **Auth.js.** С credentials он не поддерживает DB-сессии, а сброс пароля и приглашения всё равно пришлось бы писать. Своя сессия на cookie — около 100 строк.
- **Presigned URL внутри плейлиста.** Все URL протухли бы одновременно посреди просмотра, а отозванный гость продолжал бы ими пользоваться. Редирект на каждый сегмент дешевле и честнее.
- **Отдельное кодирование MP4.** MP4 копируется из 720p HLS: на одно кодирование меньше, и кадры гарантированно те же.
- **next-intl и ICU MessageFormat.** Для двух языков хватает типизированных объектов и функций с параметрами.
- **`@opentelemetry/sdk-node`** со всеми экспортёрами. `sdk-trace-node` + OTLP/HTTP легче и укладывается в лимит размера образа.
- **Готовый образ Whisper на Python/PyTorch** (2–4 ГБ). whisper.cpp из исходников — 249 МБ, работает на CPU, на amd64 и arm64.
- **React Query, Redux, Zustand, TanStack Table, repository-слои, DI, монорепозиторий.** Серверные данные приходят из RSC, у клиентских островков локальный state, Drizzle уже типобезопасный слой данных.
- **Transactional outbox.** Его заменяют sweeper и `jobId = versionId`.
- **WebSockets.** Трафик идёт только от сервера к браузеру: SSE — обычный HTTP с cookie, и он сам переподключается.
