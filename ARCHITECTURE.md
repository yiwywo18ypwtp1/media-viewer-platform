# Архитектура

## Сервисы

```
 браузер ──HTTP──► web (Next.js 16, standalone) ──► postgres (данные)
    │                 │  ▲                       ──► redis (очереди BullMQ, pub/sub)
    │                 │  └── SSE /api/events ◄── redis pub/sub
    │                 ▼
    │             presigned URL
    │
    └──PUT частей / GET медиа──► minio (S3)  ◄── worker (ffmpeg) ──► mailpit (SMTP)
                                                 ▲ очереди: media, email, maintenance
                                  migrate (миграции + seed, одноразовый)
```

- **Файлы не проходят через Next.js.** Браузер отправляет части в MinIO и получает видео напрямую по presigned URL, web только подписывает URL после проверки прав.
- **Worker — отдельный процесс и контейнер**, у которого общий с web код схемы БД, очередей и писем, но не React.
- `web` и `worker` стартуют только после того, как `migrate` завершился успешно, а postgres, redis и бакет готовы.

## Путь файла: от браузера до готовой версии

1. **Браузер.** `FileUpload` ([upload-file.ts](src/features/uploads/upload-file.ts)) — обычный TS-класс без React: конкурентность, повторы и отмена.
   - Параллельно с загрузкой Web Worker потоково считает SHA-256 (`hash-wasm`, файл не читается в память целиком).
2. **`POST /api/uploads`.** Проверка роли (editor+), MIME и размера (до 5 ГБ), `CreateMultipartUpload`, строка в `uploads`. Части по 16 МиБ.
3. **`POST /api/uploads/:id/parts`.** Presigned URL пачкой. **Права проверяются заново на каждом вызове**, поэтому удалённый участник сразу перестаёт получать URL.
4. **Браузер → MinIO.** XHR PUT `file.slice()`, 4 части параллельно, прогресс, скорость и ETA. Повтор с backoff, watchdog на зависшее соединение, пауза и отмена.
5. **`POST /api/uploads/:id/complete`.** `CompleteMultipartUpload`, `HeadObject` (сверка размера), затем транзакция под `FOR UPDATE`:
   - создаётся ассет или новая версия (номер версии считается под блокировкой ассета);
   - активное ревью на старой версии помечается устаревшим;
   - после коммита задача ставится в очередь с `jobId = versionId`.
   - Повторный `complete` возвращает ту же версию.
6. **Worker.** Скачивает оригинал потоком и в том же проходе **сверяет SHA-256 из браузера**. Затем ffprobe определяет, что это на самом деле, а не что заявил MIME.
   - Видео: постер и MP4 720p (H.264/AAC, `faststart`, без апскейла). Картинка: два WebP.
   - Результаты кладутся в `versions/<id>/…` по фиксированным ключам, так что повтор перезаписывает то же самое.
   - Ненулевой код ffmpeg — `UnrecoverableError` (без повторов). Сеть, S3 и таймаут повторяются до 3 раз с backoff.
   - Не больше 2 видео одновременно на один worker, таймаут 30 минут.
7. **Прогресс.** Каждое изменение публикуется в Redis, в Postgres пишется каждые 5%. Web раздаёт события по SSE, карточка обновляется без перезагрузки, на `ready` вызывается `router.refresh()`.
8. **Страховки.**
   - Sweeper раз в минуту ставит в очередь `pending`-версии без задачи (случай, когда Redis упал в момент `complete`).
   - Брошенные multipart-загрузки старше суток прерываются раз в час.
   - Сквозной `x-request-id` из proxy доходит до логов worker.

## Модель прав

Роли строго упорядочены: `owner > editor > reviewer > viewer`. Таблица «действие → минимальная роль» живёт в одном чистом модуле [roles.ts](src/features/workspaces/roles.ts), и его используют обе стороны:

- **Сервер** проверяет права на каждом запросе через `getProjectAccess` / `getAssetAccess`: JOIN на `workspace_members`, без кеша в сессии. Удаление участника действует мгновенно. Нет доступа — **404**, а не 403, чтобы не раскрывать существование ресурса.
- **UI** только скрывает недоступное по той же таблице.
- **`proxy.ts`** делает лишь оптимистичную проверку наличия cookie (редирект на `/login?next=…`) и CSRF-проверку `Origin` против `APP_URL` для изменяющих запросов к `/api/*`.
- Сессия — случайный токен в httpOnly cookie (`SameSite=Lax`), в БД хранится только его SHA-256. Пароли хешируются scrypt. Ссылки сброса пароля и приглашения одноразовые: атомарный `UPDATE … WHERE used_at IS NULL RETURNING`.

## Realtime

- Изменения (прогресс обработки, комментарии, ревью) публикуются в Redis-канал `events:project:<id>`.
- Web держит **одно** подписочное соединение на процесс и раздаёт сообщения SSE-потокам в памяти. Альтернатива «подписка на каждую вкладку» давала бы по соединению с Redis на каждого зрителя.
- В браузере **один** `EventSource` на страницу, события раздаются через контекст.
- Комментарии применяются чистым reducer'ом и дедуплицируются по id. Id генерирует клиент, поэтому оптимистичная копия, ответ API и эхо по SSE дают одну запись.
- Если Redis недоступен, поток не обрывается, а UI показывает «Live updates are paused».
- При SIGTERM потоки закрываются, а новые подключения получают `retry` + `Connection: close`. Иначе открытые SSE не дали бы Next завершиться gracefully.

## Согласование

- Правила — чистые функции [rules.ts](src/features/reviews/rules.ts) с тестами:
  - `any`: первое решение закрывает шаг;
  - `all`: все approve, либо первый request changes закрывает шаг;
  - `atLeast N`: N одобрений, либо changes requested, как только N уже не набрать.
- Решение принимается в транзакции: `SELECT … FOR UPDATE` строки запроса выстраивает одновременные клики в очередь → `applyDecision` → запись решения, нового шага и **итогового статуса ассета в той же транзакции**.
- Повтор с тем же `Idempotency-Key` возвращает тот же результат. Ключ уникален на (запрос, пользователь), клиент повторяет запрос при сетевом сбое с тем же ключом.
- Одно активное ревью на ассет гарантирует частичный уникальный индекс в БД.
- Письма и события отправляются после коммита. Напоминание за сутки — отложенная задача BullMQ.
- В Core один шаг (`MAX_STEPS = 1`), хранилище и транзакция уже поддерживают последовательные шаги.

## Server и Client Components

| Часть | Тип | Почему |
|---|---|---|
| Layout, шапка, inbox, списки workspaces и проектов | Server | Только данные |
| Список ассетов: сетка, таблица, тулбар сортировки и фильтров | Server | Состояние в URL, переключатели — обычные `<Link>`, клиентского JS нет |
| Бейдж обработки, `ProjectEvents` (SSE) | Client | `EventSource` |
| Загрузчик, «New version» | Client | File API, XHR, Web Worker |
| Формы auth, workspace, приглашений | Client (только форма) | React Hook Form; страница вокруг серверная |
| Страница ассета: заголовок, метаданные, стек версий, панель ревью | Server | Данные; кнопки решения и мастер ревью — клиентские островки |
| `ReviewWorkspace`: плеер, таймлайн, комментарии, аннотации | Client | Им нужен общий `<video>`. Время плеера не в state (см. ниже) |

**Мутации.** Если в разделе 4 ТЗ есть эндпоинт (загрузки, комментарии, ревью), UI обращается к нему через `fetch`: нужны `If-Match`, `Idempotency-Key`, коды 201/409/412. Server Actions используются там, где эндпоинта нет: auth, workspaces, приглашения, повтор обработки. Логика — в серверных модулях фичи, обработчики тонкие. Zod-схемы общие для формы и сервера.

## Производительность

Главное решение: **текущее время видео не хранится в React state и не передаётся через context.** Таймкод и бегунок обновляются через `requestAnimationFrame` напрямую в DOM через ref ([use-video-time.ts](src/features/player/use-video-time.ts)). Видимость аннотаций читается из элемента через `useSyncExternalStore`. Незаконченная фигура — локальный state слоя рисования (portal поверх видео), поэтому рисование не трогает список комментариев. `memo`/`useMemo` не используются: их заменяет правильный разрез состояния.

**Замер (Chromium, M-серия, видео 1080p).** 500 маркеров на таймлайне и 300 тредов в панели, 3 секунды воспроизведения:
- кадры p95 **16.7 мс**, максимум **16.8 мс**, ни одного кадра дольше 50 мс;
- **0** изменений DOM вне таймкода и бегунка;
- во время рисования пером **0** изменений в списке комментариев.

**Как воспроизвести:**
1. Создать 500 комментариев к версии видео:
   ```sql
   insert into comments (id, version_id, author_id, body, timecode_ms, created_at)
   select gen_random_uuid(), '<version_id>', (select id from users where email='editor@example.com'),
          'Note #' || g, g * 299, now() - (500 - g) * interval '1 second'
   from generate_series(1, 500) g;
   ```
2. Открыть страницу ассета и 14 раз нажать «Load more comments» (300 тредов).
3. Запустить воспроизведение и выполнить в консоли:

## От чего отказались

- **Auth.js.** С credentials он не поддерживает DB-сессии, а сброс пароля и приглашения всё равно пришлось бы писать. Своя сессия на cookie — около 100 строк, которые можно объяснить.
- **Cache Components (PPR) Next 16.** Все страницы персональные и realtime, статической оболочки нет, а флаг требовал бы `<Suspense>` вокруг каждого чтения сессии. В следующем мажоре Next он станет обязательным.
- **React Query, Redux, Zustand.** Серверные данные приходят из RSC, у клиентских островков локальный state. Единственный кеш на клиенте — страницы комментариев, и это 30 строк.
- **TanStack Table.** Таблица ассетов сортируется в SQL через URL, клиентская таблица добавила бы только вес бандла.
- **Repository/service-слои и DI.** Drizzle уже типобезопасный слой доступа к данным. Логика лежит в модулях фич, отдельный модуль появляется только там, где есть второй вызывающий (API и рендер страницы).
- **Transactional outbox** для задач обработки. Его заменяет sweeper, а `jobId = versionId` делает повторную постановку безопасной.
- **WebSockets.** Трафик идёт только от сервера к браузеру, SSE — обычный HTTP с cookie, а `EventSource` переподключается сам.
- **Монорепозиторий.** Worker делит с web схему и типы обычным импортом и собирается esbuild в один файл.
